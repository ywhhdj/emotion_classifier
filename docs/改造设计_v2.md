### 0.1 由事实直接推出的三条判断

1. **换基座的收益上限很高**：现有编码器是"语义相似度"句向量模型，句向量对副词/否定/程度不敏感（README 自述的短文本歧义正是这个病因）；XLM-R 的 token 级交互 + `[CLS]` 分类头能直接修这类错误。
2. **真正的瓶颈是 en/ja 数据量**：每类每语仅 16–36 条，任何模型都学不出判别边界 —— 回译（步骤三）与跨语言扩充（步骤四）的收益很可能**大于**换基座本身。
3. **"冻结编码器 + 预编码缓存"这一架构必须动**：现有 `stage_embed` 把文本烘成 `embeddings.npz` 再训头，一旦编码器参与训练（LoRA/解冻），缓存即刻失效。这是本次改造**最大的结构性改动**（见 §2.2.1）。

## 1. 目标、验收指标与两条路径

### 1.1 目标

- **G1 换对基座**：XLM-RoBERTa-base 取代 MiniLM，作为唯一编码器；
- **G2 提准确度**：三语 macro-F1 从 <0.70 提到 **≥0.80**，且 en/ja 与 zh 的 macro-F1 差距 **≤5 pt**；
- **G3 轻量化**：交付体积 ≤ **160 MB(fp16) / 80 MB(int8)**，CPU 单句 p50 相比 MiniLM 方案不劣化；
- **G4 语言聚焦**：词表与权重仅保留 zh/en/ja；
- **G5 架构**：`src/` 对外 Python API **零 breaking change**，内部前向/分词下沉到 Rust。

### 1.2 验收 KPI

| 指标 | 现状 | 目标 | 测量 |
|---|---|---|---|
| 三语 macro-F1 | <0.70（README 自述） | **≥0.80** | 固定测试集，5 折 CV 报均值±std |
| zh / en / ja 分语 macro-F1 | zh 高、en/ja 低 | 极差 ≤5 pt | `--stratify-lang` 分层划分 |
| 短文本歧义样本集（人工 100 条） | 有错判 | 召回 ≥90% | `tests/hard_cases.csv` |

| CPU 单句 p50（4 线程） | 基线 `T0` | ≤ `T0`×1.2 | `scripts/bench.py` |
| 词表 | 250002 | 32k–48k | `len(tokenizer)` |
| UNK 率（三语各 10k 句） | — | <0.5% | `scripts/vocab/check_vocab.py` |

### 1.3 两条主路径（必须都跑，用数据决策）

| | 路径 A：LoRA 端到端微调（推荐主线） | 路径 B：冻结编码器 + prompt 完形（备选/基线） |
|---|---|---|
| 编码器 | XLM-R-base，前 8 层冻结，后 4 层 LoRA(r=8) | XLM-R-base 全冻结 |
| 输入 | 原文（+ 可选 lang token） | 模板句，`[MASK]` 处预测情感词 |
| 训练 | 端到端，文本级 DataLoader | 可沿用现有"预编码 → 训头"两段式 |
| 成本 | 需 GPU，1 次约 20–40 min | 几乎可在 CPU 上跑，1 次 <10 min |
| 抗过拟合 | 中（靠 LoRA + 正则） | 强（可训参数仅分类头） |
| 预期上限 | 高 | 中 |

**决策规则**：先跑 B（成本极低，当作新基座的 sanity check 与 baseline），再跑 A；若 A 的 CV macro-F1 相对 B 提升 <1.5 pt，说明数据仍是瓶颈，选 B + 数据扩充优先，把算力投到回译/跨语言扩充上。

## 2. 五步改造设计

### 2.1 第一步：编码器更换为 XLM-RoBERTa-base

#### 2.1.1 为什么必须换

`paraphrase-multilingual-MiniLM-L12-v2` 是在**语义相似度/复述对**上做对比学习的句向量模型，目标是让"同义句向量靠近"，这会**主动抹掉**与相似度无关的信息——而情感分类恰恰需要保留程度副词、否定、情绪词的细微差别。README 自述的两个症状（多语言 <70%、"I happily lowered my head" 判成害羞）都是句向量模型的典型失效。XLM-R-base 在 100 种语言 CommonCrawl 上做 MLM 预训练，跨语言对齐能力显著强于 MiniLM 系列，是跨语言情感分类被反复验证的小样本基座。

#### 2.1.2 改动清单（文件级）

| 文件 | 改动 |
|---|---|
| `train/config.py` | `MODEL_NAME = "xlm-roberta-base"`；`INPUT_DIM = 384 → 768`；新增 `MAX_SEQ_LEN = 48`、`POOL_STRATEGY` 语义重定义、`USE_LANG_TOKEN` |
| `train/models.py: ONNXEncoder` | 语义从"句向量模型"改为"XLM-R 编码器 + 池化"：默认 `tokenizer_name` 改 `xlm-roberta-base`；删掉 `token_type_ids` 分支（XLM-R 不需要）；输出 3 维时按 attention_mask 做 mean pooling 的逻辑保留；`max_tokens/overlap` 分块逻辑**默认关闭**（数据 max 45 字符，无长文本） |
| `train/models.py: ChunkedEncoder` | 废弃（MiniLM 专用，随 sentence-transformers 一起降为可选依赖） |
| `train/train.py: stage_embed` | 改用 XLM-R tokenizer（`add_special_tokens`、`max_length=48`、`truncation`、`padding`），保留 npz 缓存仅供**路径 B** 使用 |
| `train/train.py: stage_onnx` | **从"只导分类头"改为"导出 encoder+head 整图"**（见 §3.5） |
| `src/models/encoder.py` | `EXPECTED_DIM = 384 → 768`；推理侧改为整图 single-session（见 §4.3） |
| `src/models/config.py` | `ENCODER_TOKENIZER = "xlm-roberta-base"`；`download_url` 去掉 sentence-transformers MiniLM 分支；`CHECKSUMS` 全量更新；`VERSION 0.1.1 → 0.2.0`；`find_encoder_onnx` 改为查找 `xlmr_*.onnx` 或统一整图 `emotion_classifier.onnx` |
| `src/predictor.py` | `__init_encoder`/`__init_backend` 合并为一次 session 初始化；对外 `predict / predict_batch / predict_proba / predict_label / get_labels` **签名与返回结构保持不变** |
| `setup.py`、`requirements.txt` | `transformers` 提为主依赖；新增 `peft>=0.10`、`accelerate`、`datasets`（训练 extras）；`sentence-transformers` 移入 `legacy` extras；`onnxruntime` 保持 |
| `README.md` | 编码器、体积、已知限制、致谢全部更新 |

#### 2.1.3 三个必须注意的 XLM-R 细节

1. **没有 `token_type_ids`**：现有 `_pack()` / `__build_feeds()` 会为 `token_type_ids` 填零，XLM-R 前向不需要；保留无害，但导出 ONNX 时不要把它放进输入签名。
2. **position_ids 从 `padding_idx+1 = 2` 起算**：HF 内部用 `create_position_ids_from_input_ids` 按非 pad token 累计生成。自实现前向（尤其 Rust 侧）必须复现该逻辑，否则右 padding 的短句位置编码全错，精度可掉 3–10 pt。
3. **tokenizer 是 SentencePiece 慢分词器**：`AutoTokenizer.from_pretrained("xlm-roberta-base")` 得到的是 `XLMRobertaTokenizer`；导出/部署前建议 `tokenizer.save_pretrained()` 时一并产出 `tokenizer.json`（fast）以便 Rust 侧统一，或直接用 `sentencepiece.model`（与训练期完全一致，推荐）。

#### 2.1.4 池化与 max_len

- 极短文本（均值 9 字符）：`MAX_SEQ_LEN = 48`（P99 覆盖，en 分词后仍宽裕），相比原 120/128 的设定，**计算量直接降到约 1/3**；
- 池化策略：`[CLS]`（XLM-R 的 `<s>`）与 mean pooling 都跑一遍 CV，`[CLS]` 通常在分类任务上更稳，mean 在极短文本上更鲁棒；建议 `[CLS] + mean` 拼接（768 → 1536）作为可选增强项，只有当 CV 提升 ≥1 pt 时才采用（会增大分类头）。

### 2.2 第二步：解冻编码器 + LoRA，而不是只训分类头

#### 2.2.1 结构性改动：预编码缓存必须废掉（最重要）

现有：`stage_embed` 把 train/val/test 全部烘成向量存 `embeddings.npz` → `stage_train` 用 `TensorDataset(X, y)` 只训 384→128→18 的头。
问题：编码器一旦参与训练，**每条 epoch 的向量都在变**，缓存立刻失效。

改造后（`train/train.py`）：

```python
# 新增：文本级数据集（LoRA / 全量微调路径）
class TextClassificationDataset(torch.utils.data.Dataset):
    def __init__(self, texts, labels, tokenizer, max_len=48, lang=None, lang_tokens=None):
        self.texts, self.labels = list(texts), np.asarray(labels, dtype=np.int64)
        self.tok, self.max_len = tokenizer, max_len
        self.lang = list(lang) if lang is not None else None
        self.lang_tokens = lang_tokens or {}

    def __len__(self): return len(self.texts)

    def __getitem__(self, i):
        t = self.texts[i]
        if self.lang is not None:                       # 可选：<zh>/<en>/<ja> 前缀
            t = f"{self.lang_tokens.get(self.lang[i], '')}{t}"
        enc = self.tok(t, truncation=True, max_length=self.max_len)
        return {"input_ids": enc["input_ids"], "attention_mask": enc["attention_mask"],
                "labels": int(self.labels[i])}

def collate(batch, pad_id=1):
    m = max(len(b["input_ids"]) for b in batch)
    ids  = torch.full((len(batch), m), pad_id, dtype=torch.long)
    mask = torch.zeros((len(batch), m), dtype=torch.long)
    for i, b in enumerate(batch):
        ids[i, :len(b["input_ids"])] = torch.tensor(b["input_ids"])
        mask[i, :len(b["input_ids"])] = 1
    return {"input_ids": ids, "attention_mask": mask,
            "labels": torch.tensor([b["labels"] for b in batch])}
```

保留旧路径：`stage_embed` + `TensorDataset` 继续服务**路径 B（冻结编码器）**，两条路径通过 `--train-mode {e2e,cached}` 切换，不互相破坏。

#### 2.2.2 LoRA 接入方式

```python
# train/models.py 新增
from transformers import XLMRobertaForSequenceClassification
from peft import LoraConfig, get_peft_model

def build_encoder_lora(num_labels: int, cfg) -> torch.nn.Module:
    model = XLMRobertaForSequenceClassification.from_pretrained(
        "xlm-roberta-base", num_labels=num_labels,
        hidden_dropout_prob=cfg.DROPOUT, attention_probs_dropout_prob=cfg.DROPOUT,
    )
    # 1) 冻结全部 encoder 参数
    for p in model.roberta.parameters():
        p.requires_grad = False
    # 2) 只解冻最后 4 层（8~11）
    for layer in model.roberta.encoder.layer[cfg.LORA_UNFREEZE_FROM:]:   # 默认 8
        for p in layer.parameters():
            p.requires_grad = False      # 基础权重仍冻结，仅由 LoRA 提供可训练增量
    # 3) 在最后 4 层挂 LoRA
    lora_cfg = LoraConfig(
        r=8, lora_alpha=16, lora_dropout=0.05, bias="none", task_type="SEQ_CLS",
        target_modules=["query", "value"],          # 注意：XLM-R 用 query/key/value，不是 q_proj/v_proj
        layers_to_transform=list(range(cfg.LORA_UNFREEZE_FROM, 12)),
    )
    model = get_peft_model(model, lora_cfg)
    return model
```

要点：

- **模块名坑**：HF 的 `XLMRobertaSelfAttention` 用的是 `self.query / self.key / self.value`（不是 `q_proj/v_proj`），写错会静默退化成"零个可训练模块"；
- **"解冻后 4 层"的正确实现**：基础权重保持冻结、只在这 4 层插 LoRA 适配器（等价于"让最后 4 层具备可训练的低成本增量"）。若要真正解冻权重，则 `requires_grad=True` 并配更小的 lr（1e-5）——**2556 条数据下不建议真解冻**；
- **分类头**：保留现有残差 MLP 结构，只是 `input_dim 384 → 768`。可直接用 `LightEmotionClassifier(768, 18, 128)` 接在 `model.roberta` 的 `[CLS]` 之上（此时 `XLMRobertaForSequenceClassification` 的自带 head 弃用，或反过来用自带 head、MLP 作为二级精炼，二者取一，CV 决定）；
- **可训参数量**：LoRA(r=8) 在 4 层的 query/value 上约 **0.6 M** + head MLP 约 **0.13 M**，合计 <0.8 M，相对 278 M 基座极小，2556 条数据不会爆显存；
- **合并**：训练结束 `model.merge_and_unload()`，得到与标准 XLM-R 结构完全一致的权重，再进入剪枝 / 导出 / Rust 内核。

#### 2.2.3 训练配方（在现有配方上增量修改）

| 项 | 现有值 | 建议值 | 说明 |
|---|---|---|---|
| lr | 5e-4（只训头） | LoRA 1e-4 / head 5e-4 | 分组 lr，`param_groups` 分开 |
| epochs / early_stop | 120 / 40 | **20 / 6** | 端到端微调不需要 120 轮，早停阈值同步下调 |
| batch_size | 64 | 32（端到端） | 序列级 batch，显存换稳定 |
| optimizer | AdamW | AdamW + **LLRD 0.9** | 越靠近输入 lr 越小 |
| schedule | CosineAnnealingWarmRestarts | 保留，T_0=5 | 周期随 epoch 数下调 |
| EMA | 已有（0.999） | 保留 | 小数据集收益明显 |
| MixUp | 0.2（向量层） | **改到 embedding 后 hidden 层**或直接关闭 | 序列级 MixUp 需重实现，先关掉做对照 |
| Focal / class-weight / label-smoothing | 已有 | 保留 | 已有，别丢 |
| R-Drop | 无 | 加，α=0.5 | 两次前向 + 对称 KL，小数据稳定性提升 |
| FGM | 无 | 加，ε=0.5（embedding） | 边界类（害羞/难为情、紧张/慌张）收益 |
| 评估 | 单折 | **5 折 CV + 固定测试集** | 已有 `cross_validate`，改为 e2e 版本 |

### 2.3 第三步：用回译替代 EDA

#### 2.3.1 现状问题

`train/augment.py: EDAAugmentor` 对中日文是破坏性的：`random_delete / random_swap / random_insert` 全部按**字符**操作，中文尚可勉强，日文一旦删掉一个假名/汉字，句子语法与情感词就散了；`punctuation` 把 `。` 换成 `！` 会直接改变情感标签（平静 → 生气）。而 `oversample_minority` 又只对少数类做这种破坏性增强，等于给标签里掺噪声。

#### 2.3.2 改造方案

```python
        ...
```

| 设计项 | 取值 / 做法 |
|---|---|
| 翻译引擎 | **首选 `facebook/nllb-200-distilled-600M`**（本地、离线可复现、支持 zho/jpn/eng/deu/fra 全部目标语）；次选 M2M100-418M；有预算再考虑商业 API |
| 路径 | zh → en → zh；ja → en → ja；en → de/fr → en（pivot 固定 en，避免二次误差放大） |
| 采样 | 出→回各采样 2 个候选（num_beams=4 / top-p 0.9），取 1–2 条通过闸门的 |
| 质量闸门 | ① 往返 char-3gram Jaccard ∈ [0.45, 0.95]（过近=无增益，过远=语义漂移）；② 长度比 [0.6, 1.7]；③ 语言检测与源语言一致；④ 去重；⑤ **不通过就直接丢弃，不做兜底** |
| 作用范围 | **只作用于 train**；val/test 保持纯净（沿用现有约定） |
| 配额 | BT 样本不超过原训练集的 100%，且每类每语增量后不超过该类 zh 样本量 |
| 缓存 | `data/bt_cache.jsonl`（`{src, lang, label, candidates, scores}`），重跑不重复花钱/算力；CI 只读缓存 |

预期：en/ja 每类 16–36 条 → 回译后 32–72 条，配合跨语言扩充（§2.4）把低资源语言拉到可训练区间。

### 2.4 第四步：跨语言扩充（zh/en → ja/en）

`data/emotion.csv` 已有 `lang` 列，直接按"高资源 → 低资源"翻译扩充：

| 源 | 目标 | 规模（约） | 说明 |
|---|---|---|---|
| zh（1863） | ja | +1200 | 主要补 ja（337 → ~1500） |
| zh（1863） | en | +800 | 补 en（356 → ~1150） |
| en（356） | ja | +300 | 英源翻译体更接近日语自然表达 |
| ja（337） | en | +250 | 反向平衡 |

执行要点：

- 目标配额 **zh : en : ja ≈ 4 : 3 : 3**（当前 7.3 : 1.4 : 1.3），-en/-ja 每类 ≥40 条；
- 划分用 `--stratify-lang`（现有 CLI 已支持 `标签×语言` 分层），保证 val/test 三语比例一致；
- **MT 文本与真实语料有分布偏差**：扩充比控制在 1:1 以内，且**只用 MT 数据做"扩充"、绝不替换真实样本**；训练时给 MT 样本加 `is_mt` 权重（如 0.7）或单独做一轮消融，验证是否真的带来增益；
- 译文需过与 §2.3 相同的语言检测 + 去重闸门；**同文本跨语言重复**（如 zh 原文与 ja 译文同时存在）应保留但打上 group id，划分时按 group 整组划分，避免 train/test 泄漏。

---

### 2.5 第五步：冻结编码器 + prompt 完形填空（备选路径 B）

#### 2.5.1 做法

把分类重构为 MLM 完形任务，编码器完全冻结，只训极小的映射层：

| 语言 | 模板 |
|---|---|
| zh | `这句话的情感是[MASK]。{text}` |
| en | `The emotion of this sentence is [MASK]. {text}` |
| ja | `この文の感情は[MASK]です。{text}` |

- **verbalizer**：18 个标签映射到标签词（高兴/平静/…；joy/calm/…；嬉しい/穏やか/…）。多 token 标签词取首 token，或对该词所有 token 的 logits 取均值；
- **可训参数**：verbalizer 映射矩阵（18 × hidden）+ 可选的一个浅 MLP ≈ 0.1 M；
- **训练**：在 `[MASK]` 位置的 hidden state 上做 18 类 softmax（或直接约束到 verbalizer token 集合的 MLM logits），CE / Focal 沿用现有实现。

#### 2.5.2 与现有 pipeline 的兼容点（关键）

模板固定 ⇒ `[MASK]` 位置的 hidden state **可以离线预计算并缓存**。因此路径 B **完全沿用现有的 `stage_embed → embeddings.npz → stage_train` 两段式**，只需把"句向量"换成"prompt-mask 向量"：

```python
# train/models.py 新增
class PromptMaskEncoder:                 # 与 ONNXEncoder 同接口，可无缝替换
    def encode(self, texts, lang=None, batch_size=32, normalize=False) -> np.ndarray:
        templated = [TEMPLATES[lang or detect(t)].format(text=t, mask="[MASK]") for t in texts]
        ...  # 前向一次，取 [MASK] 位置的 last_hidden_state
```

这样路径 B 的改造量极小（一个新编码器类 + 一个 `--train-mode cached --prompt` 开关），**1 小时内就能拿到 XLM-R 基座的第一个数字**，用来判断换基座本身是否有效、以及后续算力该投在哪。

#### 2.5.3 取舍

| | 路径 A（LoRA 端到端） | 路径 B（冻结 + prompt） |
|---|---|---|
| 可训参数 | ~0.8 M | ~0.1 M |
| 过拟合风险 | 中 | 低 |
| 上限 | 高（编码器适配到任务） | 受限于"预训练知识能否被 prompt 唤起" |
| 工程量 | 大（要重写训练循环） | 小（复用现有两段式） |
| 推理成本 | 1 次前向 | 1 次前向（模板固定，可省掉 verbalizer 头） |

**执行顺序**：B 先跑（作 sanity check + baseline）→ A 再跑 → CV 对比 → 决策。若 A 相对 B 提升 <1.5 pt，说明瓶颈在数据，转向 §2.3/§2.4 加大数据投入。

## 3. 轻量化（在换基座之后，不与之冲突）

### 3.1 参数构成与裁剪收益

`xlm-roberta-base`（hidden 768 / 12 层 / 12 头 / FFN 3072 / vocab 250002）：

| 部件 | 参数量 | 占比 |
|---|---|---|
| word embedding | 250002 × 768 = **192.0 M** | **69.0%** |
| position embedding + LN | 0.40 M | 0.1% |
| 12 × Transformer 层 | **85.0 M** | 30.6% |
| pooler + 18 类分类头 | 0.60 M | 0.2% |
| **合计** | **278.0 M** | 100%（fp32 ≈ 1112 MB） |

本任务是**分类**而非生成，**没有 LM head**，因此词表裁剪只影响输入 embedding —— 这是相对生成式模型裁剪的巨大简化点。

### 3.2 三语词表裁剪

**保留判定（并集）**：特殊标记（`s/pad/</s>/unk/mask` + 新增 `zh/en/ja`）∪ 白名单（字节回退 `<0x00>~<0xFF>`、ASCII 全集、常用标点、数字、emoji/颜文字——短文本情感强信号）∪ 三语语料覆盖（频次 ≥2）∪ Unicode script ∈ {Han, Hiragana, Katakana, Latin, Common, Inherited}。
**删除**：Cyrillic / Greek / Arabic / Hebrew / Devanagari / Thai / Hangul / 其他非目标 script。

> 日语汉字与中文本就同属 Han 区块，天然共享；全角标点 `。、，` 属 Common，自动保留。

| 路径 | 工具 | 定位 |
|---|---|---|
| **P1 主路径** | `textpruner.VocabularyPruner` | 训练流水线内，官方对 XLM-R 有一等支持（XNLI 示例即 XLM-R） |
| **P2 对照** | `hf-trim` 方法学 | 仅作离线校验与兜底；hf-trim 原生**只支持 BART/mBART/T5/mT5，不含 XLM-R**，需自研 `XLMRTrimmer`；且它不支持 fast tokenizer，而 XLM-R 底层是 SentencePiece，裁剪后必须同步重写 `sentencepiece.model` |
| **P3 产物路径（推荐）** | 新训三语 SentencePiece 取交集 | ① 三语语料训新 BPE（32k–48k，`character_coverage=0.9995`，`byte_fallback=true`）② 取 **新词表 ∩ 原 XLM-R 词表** ③ 交集中 token 的 embedding 行**直接从 `xlm-roberta-base` 复制** ④ encoder 其余权重原样 copy ⑤ 产物自带自洽 `.model` |

P3 自带自洽的 SentencePiece 模型，HF 与 Rust `sentencepiece` crate 都能直接加载，**无 ID 错位风险**，推荐作为最终产物方案。

```python
# P1 示例（scripts/vocab/trim_vocab.py）
from textpruner import VocabularyPruner, VocabularyPruningConfig, GeneralConfig
pruner = VocabularyPruner(model, tokenizer,
        vocabulary_pruning_config=VocabularyPruningConfig(min_freq=2),
        general_config=GeneralConfig(device="cuda", output_dir="./ckpt/vocab_pruned"))
pruner.prune(dataiter=trilingual_corpus,
             additional_tokens=["<s>","<pad>","</s>","<unk>","<mask>","<zh>","<en>","<ja>",
                                *byte_fallback, *emoji_whitelist],
             save_model=True)
```

**裁剪后强制校验**（`scripts/vocab/check_vocab.py`，CI 必跑）：

- `len(tokenizer) == model.config.vocab_size == embedding.weight.shape[0]`
- 特殊标记 id 均 < vocab_size，encode/decode 正常
- 三语各 10k 句 UNK < 0.5%，平均 subword 数增长 < 10%
- encode→decode 往返无损抽检 1000 条
- emoji / 数字 / URL / 中英混排（"这个 bug 太 annoying 了"）分词正常
- 三语各 200 条前向，logits 与裁剪前**符号一致**（防 embedding 行错位）

### 3.3 裁剪后必须"复活"

1. 先只训 embedding + 分类头 0.5 epoch（lr 5e-5），再进主训练；
2. **DAPT**（三语域内语料 MLM 1–2 epoch，lr 1e-4，mask 15%）优先于直接微调，把新 embedding 拉回语义空间；
3. 掉点 > 2 pt 说明裁过头，升档到配置 C。

### 3.4 编码器结构化剪枝（TextPruner）

```json
{ "pruning_method": "iterative", "target_ffn_size": 1536, "target_num_of_heads": 8,
  "n_iters": 12, "head_even_masking": true, "ffn_even_masking": true,
  "multiple_of": 64, "use_logits": false }
```

- `n_iters=12~16` 是精度保护的关键（逐步按重要性裁剪，单卡十余分钟）；
- `multiple_of=64` 保证 FFN 维度整齐，避免 shape 不整齐吃掉加速收益；
- 剪枝用的 dataloader **必须三语混合**，否则会剪掉中日语专属注意力头，跨语言能力塌方；
- 剪枝后必须做**同任务蒸馏恢复**：`Loss = CE + 4~8 × MSE(student/T, teacher/T) + γ·Cos(中间层)`，teacher 用未剪枝的微调模型；无 teacher 则退化为"继续微调 2 epoch + EMA"。

### 3.5 档位与预算

| 配置 | vocab | heads | FFN | encoder | embedding | 总参数 | fp32 | fp16 | int8 |
|---|---|---|---|---|---|---|---|---|---|
| 原方案（MiniLM+头） | 119k | 12 | 3072 | 66 M | — | ~66 M | 264 MB(90 MB量化) | — | — |
| XLM-R 基线 | 250002 | 12 | 3072 | 85.0 M | 192.0 M | **278.0 M** | 1112 MB | 556 MB | 278 MB |
| **A（推荐）** | 40000 | 8 | 1536 | 47.2 M | 30.7 M | **78.9 M** | 316 MB | **158 MB** | **79 MB** |
| B（激进） | 32000 | 8 | 1024 | 37.8 M | 24.6 M | **63.4 M** | 254 MB | 127 MB | 63 MB |
| C（保守） | 48000 | 10 | 2048 | 61.5 M | 36.9 M | **99.3 M** | 397 MB | 199 MB | 99 MB |

叠加 `MAX_SEQ_LEN=48`（原 120/128），端到端实测 CPU 加速预期 2.0–2.6×。默认交付 A，掉点 >2 pt 回退 C。

### 3.6 完整流水线的正确顺序

```
词表三语裁剪 → DAPT(MLM) → [路径A: LoRA端到端微调 | 路径B: prompt+冻结训头]
   → merge_and_unload(仅路径A) → 评测闸门
   → TextPruner 编码器剪枝 → 蒸馏恢复 → 温度/阈值校准 → ONNX 整图导出 + 量化 → Rust 内核
```

> 顺序原则：词表裁剪必须**在微调之前**（否则裁剪掉的行白训）；剪枝必须**在微调之后、蒸馏之前**；LoRA merge 必须在剪枝之前（剪枝工具需要看到完整权重）。

### 3.7 导出与量化

- **导出整图**而非只导分类头：`torch.onnx.export(model, (ids, mask), ..., input_names=["input_ids","attention_mask"], output_names=["logits"], dynamic_axes={0:"batch", 1:"sequence"})`，opset **17**（现有代码已注释 18 在部分 runtime 上不支持 LayerNorm 融合）；
- `onnxsim` 简化 → `onnx.checker` → FP16（`keep_io_types=True`）→ INT8 动态量化；
- 保留现有的"FP32 vs 量化最大偏差自检"逻辑，阈值放宽到 batch 1/2/8 全过；
- 三档产物 + 一份 `calib.json`（temperature + per-class 阈值），供推理侧加载。

## 4. Rust 内核 + `src/` Python 胶水层

### 4.1 crate 划分

```

├── Cargo.toml                       # workspace

│   ├── emotion-core/                # 类型、错误、配置、指标

```

依赖：`thiserror` `serde` `rayon` `pyo3`(abi3) `numpy` `tracing` + 后端 `candle` 或 `ort`。

### 4.2 后端选型

| 方案 | 结论 |
|---|---|
| **`candle`（纯 Rust）** | **默认**：无 C 依赖、易交叉编译（musl/ARM）、safetensors 加载快，需手写 XLM-R 前向 |
| **`ort`（onnxruntime）** | feature `backend-ort`：服务端 GPU / 高吞吐，直接复用 ONNX 产物 |
| `tch`(libtorch) | 不选（>200 MB 依赖，与轻量化冲突） |

用 `trait Backend { fn forward(&self, ids, mask) -> Array2<f32> }` 抽象，Python 层无感。

### 4.3 `src/` 侧改造（保持对外 API 零变化）

- `src/models/encoder.py`：`EXPECTED_DIM = 384 → 768`；新增 `RustEngineEncoder(BaseEncoder)`，与 `ONNXEncoder` / `SentenceTransformerEncoder` 并列，`__init_encoder` 按可用性依次尝试 **Rust → ONNX → PyTorch**；
- `src/models/config.py`：新增 `ENCODER_BACKEND = "rust" | "onnx" | "pytorch"`、`EXPECTED_DIM = 768`；
- `src/predictor.py`：整图模式下 `__init_encoder` 与 `__init_backend` 合并为一次初始化；`predict / predict_batch / predict_proba / predict_label / get_labels` **签名与返回结构完全不变**；
- 新增：`src/runtime.py`（引擎单例与 warmup）、`src/threshold.py`（`calib.json`）、`src/languages.py`（lang 归一化）、`src/exceptions.py`、`src/legacy.py`（兼容旧入口）；
- 构建：新增 `pyproject.toml`（`maturin` build-backend，`abi3-py310`，`python-source = "src"`），产物 `emotion_classifier._core`；模型权重不进 wheel，走 `from_pretrained`/缓存目录；
- 无 Rust 工具链的环境回退到 ONNX Runtime 纯 Python wheel（`EMOTION_BACKEND=onnx`）。

### 4.4 两个必须对齐的点

1. **分词一致性**：Rust 侧直接用裁剪产物自带的 `sentencepiece.model`，与训练期完全一致；归一化顺序固定 `NFKC → 空白折叠 → 控制字符清理 → 保留 emoji → lang 判定 → 拼 lang token → spm encode → 截断 48`；CI 用 1 万条样本比对 Python/Rust 的 id 序列，**必须完全相同**。
2. **position_ids 偏移**：见 §2.1.3，自实现前向必须复现 `create_position_ids_from_input_ids`；加一条"右 padding 短句与单条推理 logits 一致"的单测。

### 4.5 PyO3 绑定要点

```rust
#[pymethods]
impl EmotionEngine {
    fn predict(&self, py: Python<'_>, texts: Vec<String>, top_k: usize,
               lang: Option<Vec<String>>) -> PyResult<Vec<Vec<(u16, f32)>>> {
        py.allow_threads(|| self.inner.predict(texts, top_k, lang))   // 释放 GIL
    }
    fn forward_ids<'py>(&self, py: Python<'py>, ids: PyReadonlyArray2<i64>,
                        mask: PyReadonlyArray2<i64>) -> PyResult<Bound<'py, PyArray2<f32>>> {
        let out = py.allow_threads(|| self.inner.forward(ids.as_array(), mask.as_array()))?;
        Ok(out.into_pyarray(py))                                      // 零拷贝
    }
}
```

批调度：请求入队 → 满足 `max_batch=32` 或 `max_wait=2 ms` 打包 → 批内按长度 bucketing；权重 `mmap` + `Arc` 共享，多 Python 线程复用同一份。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 现有"预编码缓存"架构与端到端微调冲突 | 主流程要重写 | 双模 `--train-mode {e2e,cached}`，路径 B 复用现有两段式，先出数再重构 |
| 2556 条数据端到端微调过拟合 | 掉点 | LoRA r=8 + 前 8 层冻结 + EMA + R-Drop + 5 折 CV；epochs 从 120 降到 20 |
| 回译译文质量差、引入标签噪声 | 反而掉点 | 三重质量闸门 + 丢弃不兜底 + 缓存可回滚 + 单独消融验证增益 |
| 跨语言扩充造成 train/test 泄漏 | 指标虚高 | 按原文 group 整组划分；`--stratify-lang` |
| 词表裁剪后 UNK 上升 | 中日语掉点 | vocab ≥32k、min_freq=2、字节回退与 emoji 全保留；掉点 >2 pt 升档 C |
| SentencePiece 模型与裁剪词表不一致（静默错误） | 精度崩溃 | 优先 P3 交集法（自洽 `.model`）；§3.2 全量校验入 CI |
| hf-trim 不支持 XLM-R | 工具链受阻 | 主路径用 textpruner，产物路径用 P3，hf-trim 仅作方法学参考 |
| XLM-R 自实现前向出错（position_ids / 无 token_type_ids） | 精度异常 | 专项单测 + 与 PyTorch logits 对齐测试作为 CI 门禁 |
| 包体积从 90 MB 涨到 158 MB | 与"轻量"目标冲突 | 词表裁剪 + 剪枝把参数压到 78.9 M；int8 档 79 MB，与原方案同量级 |
| NLLB-600M 离线部署成本 | 磁盘/时间 | 回译结果落 `bt_cache.jsonl`，只跑一次；CI 只读缓存 |
